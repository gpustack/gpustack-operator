Architecture

GPUStack Operator schedules accelerator workloads on Kubernetes. It discovers node hardware and builds isolated Kueue scheduling pools for Instances, ModelDeployments, and Pods. Model delivery resolves and caches weights, topology placement constrains failure domains, remote direct memory access (RDMA) accelerates transfers, and shared KV cache stores reusable prefixes.

Components

The gpustack-operator binary provides five service subcommands and the internal model-forger sandbox helper, paired with the engine-sentinel runtime package staged into managed inference Pods:

Component Deployment Role
worker Control-plane Deployment Serves APIs and reconciles workloads, queues, and supporting resources.
device-manager Vendor DaemonSet Discovers accelerators and NICs,
publishes capacity, and allocates devices.
model-manager Per-node DaemonSet Caches verified model weights and kernels and mounts them through CSI.
model-transfer Vendor source DaemonSet Runs the source broker and worker service, paired with the staged gpustack_model_transfer Python reader package for remote weight delivery.
model-forger ForgeSandbox Pod helper Runs built-in mock, verify, and hold helper stages for kernel specialization; see Model Deployment Forger .
worker-gateway Separate installation Aggregates InstanceTypes and capacity across clusters into one fleet view.
engine-sentinel Read-only host mount in engine Pods Pure-Python runtime package (gpustack_engine_sentinel) for live parameter tuning, unified /gpustack/v1/{live,ready} probes, role pause, and PreStop drain; see Online Runtime Control .

The Helm chart bundles Node Feature Discovery (NFD) , Kueue , and two CSI drivers. Topograph is optional and disabled until an administrator configures a topology provider. See Installation Modes for deployment modes and runtime settings.

Workload flow

GPU Instances run interactive containers with optional SSH access. ModelDeployments run managed inference roles, routers, and prefill/decode (PD) or encode/prefill/decode (EPD) groups. Both consume the same pool capacity and admission chain, while model delivery and KV cache attach only when requested.

Every optional service in the diagram can be omitted. An ordinary Pod can also request accelerator resources directly through its namespace LocalQueue.

Model delivery

A ModelArtifact separates weight sources and credentials from workload specs. It resolves and pins weights from Hugging Face, ModelScope, an OCI image, or a PersistentVolumeClaim.

Workloads load weights directly in the engine (Engine), mount verified node cache paths through the Model Manager CSI driver (Node), or mount an image or PVC. Remote delivery streams weights from prepared source nodes through model-transfer; see Remote Weight Delivery .

ModelStore and ModelStoreBinding govern node selection and namespace cache quotas. NodeModelStore reports per-node cache state, and ModelPrefetch warms weights ahead of serving without holding GPU quota. See Model Delivery , Model Artifact , and the Model Prefetch Walkthrough .

KV cache

A KVCacheBackend deploys a shared Mooncake cache cluster or connects to an external endpoint. KVCachePool and KVCachePoolBinding grant namespace access, reuse domains, and memory ceilings independently of GPU quota. Compatible ModelDeployments and labeled Pods receive client settings at creation; see KV Cache .

Model Deployment combines these capabilities with engine, router, and scaling policies. GPU Instances run interactive containers on the same accelerator pools.

Device scheduling

Device scheduling runs in four stages:

  1. NFD inspects node hardware and publishes feature labels.
  2. Device Manager detects accelerators and NICs and updates each node’s Devices ledger.
  3. The worker derives schedulable CPU and accelerator capacity labels from that inventory.
  4. The worker creates an AcceleratorType per accelerated pool (plus InstanceTypes when enabled) sharing one isolated ClusterQueue.

Heterogeneous Devices and Preflight Checks cover node readiness and isolation modes. Accelerator Requests defines resource keys, capacity views, and pool selection. See RDMA Operations for fabric requests and Topology-Aware Scheduling Operations for domain placement.

Request admission

The Pod webhook validates accelerator requests before Kueue reserves quota. Kueue AdmissionChecks verify per-device fit and multi-role gang readiness before kube-scheduler, kubelet, and the allocator bind devices; see Accelerator Requests .

AcceleratorType and InstanceType status update as workloads claim and release accelerators. Run kubectl get acctype,instancetype -w to watch live pool capacity, or follow the Heterogeneous Devices Walkthrough .

Vocabulary

Term Meaning
Pool Nodes with matching CPU, accelerator, OS, and architecture identities, served by one isolated ClusterQueue.
AcceleratorType Cluster-scoped accelerator pool for serving and prefetch workloads; short name acctype.
InstanceType Cluster-scoped workspace sizing and capacity view for Instances.
Allocation mode Whole cards, shared cards, logical slices, or hardware partitions.
Credits Quota units (credits.gpustack.ai/<manufacturer>) metered on a pool ClusterQueue.
Four capacity views Exclusive (EX), shared (SH), sliced (SL), and partitioned (PT) counts on pool status.
Devices ledger Per-node custom resource recording discovered hardware and active allocations.
LocalQueue Namespace queue entrance that routes a workload into its target ClusterQueue.
ModelArtifact Namespaced weight source and resolved manifest digest referenced by workloads.
NodeModelStore Per-node cache configuration and observed digest state.
ModelPrefetch Namespaced request to warm a ModelArtifact onto bound ModelStore nodes.

A physical card or module is a device, each schedulable unit on it is an accelerator, and the Kubernetes extended resource key a container requests is a resource.
