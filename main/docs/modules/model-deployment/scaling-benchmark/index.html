Model Deployment Scaling Benchmark

Two hardware suites evaluate ModelDeploymentScaler. Suite 1 ran five disaggregated configurations on one eight-H100 node. Suite 2 evaluated offline capacity priors, 18 serial capacity-arm rounds, 360-second algorithm sensitivity, embedded InferenceX priors and multi-node disaggregation across four single-H200 nodes.

ModelDeploymentScaler observed load shifts, resolved offline priors and updated replicas promptly. End-to-end scale-out latency still depends on weight loading, engine startup, graph compilation (~76 s on H200 vLLM) and accelerator queueing outside the scaler’s control.

Summary

A prefill/decode (PD) pair splits prompt processing from token generation; an encode/prefill/decode (EPD) deployment adds an image encoder. Suite 1 compared Proportional, TokenThroughput and Predictive on H100; Suite 2 evaluated Server capacity priors and multi-node PD/EPD on H200. Model Deployment Scaling defines the algorithms, priors and guards.

  • Choose catalog-backed Predictive for sustained traffic ramps where startup latency (~76 s) otherwise outlasts reactive scale-out; pair horizonSeconds with maxStepReplicas because ramp slopes amplify rawRecommendedReplicas.
  • Choose TokenThroughput with 0.75 catalog headroom for steady workloads where unmargined saturation capacities stay under-triggered.

Failures and caveats remain: Suite 1 SGLang PD hit Mooncake TCP port exhaustion (4,421 errors); the standalone lifecycle check lost 7/13,073 requests during scale-out; Suite 2 TokenThroughput failed 11/1,272 requests in 360 s sustain; and multi-node H200 vLLM PD prefill scale-out hit transient Router 503s during worker registration.

All 18 H200 single-Server rounds, the embedded openai/gpt-oss-120b check, and H200 vLLM PD Proportional and EPD Predictive completed with zero failed requests.

Benefits

  • In Suite 2 on H200 from an equal 1-replica baseline, 0.75 catalog headroom triggered TokenThroughput (1 → 2 at c = 24) where unmargined saturation (17135.159 tok/s) stalled, and the embedded openai/gpt-oss-120b (fp4) prior matched sustain throughput within 1.2% (4862.388 versus 4804.08 tok/s).
  • Pairing the catalog with Predictive offset ~76 s vLLM startup, cutting 45 s sustain TTFT p50 from 343.842 to 189.511 ms (maxReplicas: 2) and 90 s sustain TTFT p50 from 145.939–190.555 to 120.59 ms (maxReplicas: 4, 3886.136 output tok/s, zero errors).
  • In Suite 1 on H100, predictive PD cut ramp TTFT p50 (467.906 versus 2540.853 ms) and raised output (2109.251 versus 1117.481 tok/s), though low manual targets scaled it during baseline.

Trade-offs

  • In Suite 1, 90 s cooldown sat below the 300 s downward stabilization window, leaving final snapshots at two replicas.
  • In Suite 2’s 45 s sustain rounds, TokenThroughput catalog spent 317.04 median readyReplicaSeconds (+33.7% over manual’s 237.094 s) without lowering sustain TTFT p50 because ~76 s startup consumed most of the window.
  • Predictive amplifies initial ramp slopes (rawRecommendedReplicas 4–75), so production configs pair horizonSeconds (180–300 s) with behavior.scaleUp.maxStepReplicas; see Step 3: Choose an algorithm .

Configuration

Suite 1 roles started at 1 replica with bounds 1..2, Active mode and a 10 s sampling interval.

Configuration Model Algorithm Capacity settings
vllm-pd-proportional Qwen3-8B Proportional RunningRequests, target 3 per role, tolerance 0.1
vllm-pd-token-throughput Qwen3-8B TokenThroughput Prefill 1200 tok/s; decode 300 tok/s per replica
vllm-pd-predictive Qwen3-8B Predictive Same fallback targets; forecast capacity 2000 tok/s per role
sglang-pd-token-throughput Qwen3-8B TokenThroughput Prefill 1200 tok/s; decode 300 tok/s per replica
vllm-epd-predictive Qwen2.5-VL-7B-Instruct Predictive Same fallback and forecast capacities; encode coupled to prefill

Predictive runs set horizonSeconds: 30, minPoints: 2, qLevel: "0.5" and qTrend: "0.3". Token-based runs kept default 180 s stable / 60 s panic windows, panic threshold 2, and latency targets 500 ms / 50 ms. All preferred a prefill/decode ratio of 1 (EPD also preferred encode/prefill 1, reaching 1 encode, 2 prefill, 2 decode).

  sampling:
    intervalSeconds: 10  # sampling cadence

      minReplicas: 1
      maxReplicas: 2
    - name: decode
      minReplicas: 1

      denominatorRole: decode

Benchmark run order

Two waves shared an eight-GPU ceiling (maximum reserved capacity per sequence, not continuous use):

Wave First sequence Second sequence GPU ceiling
1 vLLM PD: Proportional, reset, then Predictive; up to 4 GPUs SGLang PD: TokenThroughput, release, then a separate vLLM PD TokenThroughput deployment; up to 4 GPUs 4 + 4 = 8
2 vLLM EPD Predictive; up to 6 GPUs Single-role live lifecycle check; up to 2 GPUs 6 + 2 = 8

Admission checks ran separately before Wave 1. Between configurations on a shared deployment, the runner deleted the scaler, waited for binding release and restored one replica per role.

Suite 2: Capacity priors

Suite 2 ran across four single-GPU H200 nodes plus a dedicated CPU driver node, testing offline priors on single-Pod Server deployments before re-running the five disaggregated configurations across multiple nodes.

Single-replica sweep

One Qwen/Qwen3-8B (bf16, vllm, 1 × H200, TP = 1) Server replica ran six 60-second concurrency levels (1,024/256 tokens, zero errors) to build the offline ConfigMap catalog.

Every point met P95 TTFT <= 2000 ms and ITL <= 33 ms (ExplicitSaturation). Catalog.Resolve picked 17135.159 tok/s at c = 32 as the seed and applied headroom: "0.75" to derive 12851.37 tok/s, crossing measured throughput between c = 16 (11477.608 tok/s) and c = 24 (14527.811 tok/s).

Capacity estimate comparison

Eighteen serial rounds (3 alternating repeats × 6 arms) compared frozen-manual (20000 tok/s), tuned-manual (17135.159 tok/s) and catalog (12851.37 tok/s) across nominal phase windows baseline (30 s, c = 2), ramp (45 s, c = 24), sustain (45 s, c = 24) and cooldown (30 s, c = 0). All 18 rounds finished with zero failed requests, verified UID-preconditioned cleanup and return to 1 replica.

Checkpoints (B1–C3) record phase progress, while scale-up elapsed times track wall clock from ramp start (in-flight drain and harness transitions extend actual wall time past the nominal 45 s ramp + 45 s sustain windows).

Starting from one replica on H200, unmargined TokenThroughput manual arms stayed at 1 replica (~14.5k tok/s at c = 24 sat below 17135.159 tok/s). TokenThroughput catalog triggered at R2, and after ~76 s of vLLM startup became Ready at S3 (99.6–105.6 s from ramp start), costing +33.7% median readyReplicaSeconds (317.04 versus 237.094 s) with no sustain TTFT win (343.842 versus 321.352 ms).

Predictive triggered earlier (15.1–21.9 s from ramp start) and reached Ready by checkpoint R3 (81.9–94.6 s elapsed from ramp start), cutting sustain TTFT p50 to 189.511 ms (catalog), 194.733 ms (frozen-manual) and 206.453 ms (tuned-manual).

Algorithm sensitivity

A 360-second H200 hardware wave (baseline 60 s c = 2, ramp 90 s c = 24, sustain 90 s c = 24, cooldown 120 s c = 0, maxReplicas: 4) compared Proportional (RunningRequests target 8), TokenThroughput (14000 tok/s) and catalog-backed Predictive (12851.37 tok/s) using True SLO (TTFT <= 2000 ms and adjacent ITL <= 33 ms) and Goodput.

Those metric definitions match the deterministic synthetic simulation (model output, not GPU hardware), where Predictive reached 99.4% true SLO on a five-step synthetic ramp seed against 76.1% for reactive configurations.

On the H200 hardware wave, catalog-backed Predictive reached 3 Ready replicas by R2 and 4 by R3, cutting ramp TTFT p50 from 347.282–350.591 ms to 192.093 ms and sustain TTFT p50 to 120.59 ms (3886.136 output tok/s, zero failed requests). Exception: TokenThroughput recorded 11 failed requests out of 1,272 in sustain (True SLO 0.9914), while Proportional and Predictive kept 1.0 with zero failures.

Embedded catalog

An openai/gpt-oss-120b (fp4, vllm, 1 × H200) Server deployment ran with capacityPrior: {} and no catalogRef or identity annotations against the embedded catalog. It inferred Server/openai/gpt-oss-120b/fp4/vllm/nvidia-h200/gpus=1,tp=1,ep=1,pp=1,dp=1,ldp=1,cp=1 (profileDigest: sha256:47d96f0e...), resolved seedTokensPerSecond: "6405.44" (ExplicitSaturation, P95 TTFT 2000 ms, ITL 33 ms) and set effectiveTokensPerSecond: "4804.08".

Verification

Scale-out timing

Scale-out lead measures ramp start to the first sampled desired count above 1 (not Ready time). A count already above 1 at ramp start reports 0 with Pre-ramp count >1 set to Yes.

vllm-pd-token-throughput (H100) 0 Yes Prefill 2, decode 2 Prefill 2, decode 2
vllm-pd-predictive (H100) 0 Yes Prefill 2, decode 2 Prefill 2, decode 2
sglang-pd-token-throughput (H100) 0 Yes Prefill 2, decode 2 Prefill 2, decode 2
vllm-epd-predictive (H100) 0 Yes Encode 1, prefill 2, decode 2 Encode 1, prefill 2, decode 2

In Suite 2, every single-Server run started ramp at 1 Ready replica: Predictive committed growth at 15.1–21.9 s versus 22.2–28.2 s for TokenThroughput catalog.

Retirement

The standalone single-role lifecycle check verified scale-out, serving at two replicas, Disqualified and Draining during scale-down, and serving on one survivor:

Lifecycle phase Requests Errors Observation
Scale-out (up) 13073 7 Router returned HTTP 503 with connection termination
Two replicas (two) 14810 0 Expanded deployment served requests
Scale-down (down) 1880 0 Retirement observed while traffic continued
One replica (one) 942 0 One Ready survivor served requests

The earlier Wave 2 check also recorded 3 failures in 10,579 scale-out requests. Admission passed all 45 checks; the standalone lifecycle check passed 10 checks and failed its all-phases check.

Suite 1 timelines sampled Disqualified on proportional and token-based PD (plus Admitted and Aborted on predictive PD) and no retirement state on EPD. The retirement protocol transitions Draining → Deleting (distinct from Kubernetes Terminating). Before trusting live recommendations, verify partial: false and missing[] via /metrics (Engine signals ).

Additional runtime-acceptance runs verified:

  • vLLM multi-Server manual scaling (1 → 2 → 1): Router worker set followed every edit, round_robin split 16 requests 8/8 at two replicas, and 21/21 checks passed.
  • vLLM External DP retirement (DP = 2): Router held 2 → 4 → 2 workers; withdrawal reached the Router in 21 s and retired members deleted at 70 s (honoring the 60 s handoff window). Eight checks passed; one check failed from timing withdrawal against the 60 s window (case bug).
  • SGLang PD active scaling: 29/29 checks passed; Mooncake moved 54 MB across six direct transfers with zero failures; the scaler read 24 waiting requests on decode, scaled decode to 2, and returned both roles to 1.
  • Suite 2 single-Server rounds: All 12 rounds that scaled to 2 (3 TokenThroughput catalog and 9 Predictive) returned to 1 Ready replica with zero failed requests.

Limitations

  • Suite 1 (one 8-H100 node) and Suite 2 (four 1-H200 nodes) do not establish a universal algorithm ranking or optimal headroom margin across workloads.
  • Text and multimodal clients run different work and stopping rules, so throughput values are not comparable across modes. Image tags do not prove identical internal engine packages.
  • Zero errors apply only to those measured requests: multi-node H200 PD prefill scale-out hit transient Router 503s during registration, and SGLang PD reproduced Mooncake KV transfer errors.
  • See Scaling Walkthrough for the boundary between configuration examples and captured lifecycle evidence.
