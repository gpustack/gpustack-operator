Encode, Prefill and Decode Benchmark

On one H100 SXM5 node, encode/prefill/decode (EPD) reduced long-prompt generation stalls and repeated-image latency compared with aggregated serving and prefill/decode (PD). Aggregated serving, PD and EPD used one, two and three GPUs, respectively. These results compare deployed configurations with unequal GPU budgets.

At 8k and concurrency 8, EPD reduced inter-token latency (ITL) p99 from 296.710 ms to 13.607 ms, or 21.8× lower, compared with aggregated serving. Its time to first token (TTFT) p50 was higher: 4,182.324 ms against 3,963.085 ms. Encode, Prefill and Decode describes the role contract.

The initial capture used cross-Pod TCP. The separate InfiniBand RDMA comparison adds matched follow-up measurements while retaining the TCP results and conclusions.

Configuration

Each configuration used one ModelDeployment, with one replica per role and one GPU per Pod. All serving roles ran on the same GPU node, gpu-node-0.

Configuration Roles GPUs KV connector Encoder connector
Aggregated 1 Server 1 None None
PD 1 Prefill + 1 Decode 2 MooncakeConnector, TCP None
EPD 1 Encode + 1 Prefill + 1 Decode 3 MooncakeConnector, TCP ECCPUConnector, NIXL

Each Pod exposed only its assigned GPU, with a private /dev/shm and IPC namespace. hostIPC was disabled, and no remote direct memory access (RDMA) interface was attached. All cross-Pod NIXL encoder-cache and Mooncake KV transfers used container TCP sockets over eth0. The host’s NVLink fabric was not used between roles.

Suite 1 workload

Suite 1 varied image and text length with a 128-token completion limit. Image dimensions are pixels; text-token values are generator targets. Measured prompt lengths include the model’s multimodal request formatting.

Context Image Text target Measured prompt tokens
1k 560 × 560 624 1,047–1,050
2k 840 × 840 1,148 2,071–2,074
4k 1260 × 1260 2,071 4,119–4,122
8k 1792 × 1792 4,096 8,215–8,219

Concurrency 1, 4 and 8 used 8, 12 and 24 measured requests per context, respectively.

Suite 2 workload

Two streams ran concurrently, with four workers and twelve requests each. The small stream used unique 560 × 560 images, a 624-token text target and max_tokens=256. The heavy-vision stream used unique 1792 × 1792 images, a 400-token text target and max_tokens=64. Measured prompt lengths were 1,048–1,051 and 4,520–4,523 tokens, respectively.

Suite 3 workload

Suite 3 reused one 1792 × 1792 image with a different question per request. It used a 400-token text target and max_tokens=64; measured prompts contained 4,518–4,522 tokens. Concurrency 4 and 8 used 12 and 24 measured requests.

Method

The load generator ran inside the cluster. Each configuration ran once, sequentially on the same node. Two warm-up requests preceded every Suite 1 and Suite 3 cell and were excluded from latency summaries. The 45 result files contain 36 Suite 1 cells, three mixed-load runs and six repeated-image cells. Each mixed-load file reports both streams separately.

All 708 measured requests succeeded with zero errors, 236 per configuration. Each configuration also issued 28 warm-up requests. Time per output token (TPOT) measures per-request generation time per token; ITL measures streamed-token gaps. Bold table values mark lower latency or higher throughput within each matched workload and concurrency.

At 4k and concurrency 8, EPD reduced ITL p99 from 231.453 ms to 15.352 ms, or 15.1×. TTFT p50 also fell from 1,972.504 ms to 1,690.166 ms. At 8k and concurrency 8, ITL p99 improved 21.8×, but TTFT p50 increased by 219.239 ms. Separating generation from prompt processing improved token-gap tails without consistently improving first-token latency.

Aggregated serving had the lowest TTFT p50 for every 1k cell and the lowest TTFT p95 for every 2k cell. At 8k and concurrency 4, EPD improved median TTFT but worsened its p95 against aggregated serving. The recorded medians and tails support different choices; EPD has no universal latency advantage.

The EPD Decode sidecar also logged 264 multimodal-item events. Each configuration’s router access capture contained 280 lines. These counts establish traffic at every EPD stage, but are not request-ID correlation or byte-transfer measurements. The PD Prefill count is eighteen below its Decode count; the capture does not establish the reason.

The aggregated and PD render counts are separate from completion counts. A successful response or matching aggregate counts alone cannot prove that every request traversed every intended stage. See Counting engine tokens for the router’s token-render requirement.

Summary

Benefits

  • Long-prompt generation tails improved: EPD had 15.1×–21.8× lower ITL p99 at 4k/8k, concurrency 8, than aggregated serving.
  • Repeated-image traffic reached 536.280 tok/s at concurrency 8, with 5.9× lower TTFT p50 than aggregated serving.
  • Mixed traffic completed in 5.217 s, against 8.473 s for aggregated serving, with lower first-token and token-gap tails.

Trade-offs

  • EPD used three GPUs, compared with one for aggregated serving and two for PD.
  • Small prompts often favored aggregated serving on first-token latency.
  • The 8k, concurrency-8 EPD median TTFT remained higher than aggregated serving despite much lower ITL p99.

Choose EPD for large-image generation isolation, repeated-image workloads or the measured mixed-traffic benefits when three GPUs are available. Small-prompt first-token latency can favor aggregated serving. The cross-role TCP transfers and unequal GPU budgets prevent a universal latency or equal-cost efficiency claim.

InfiniBand RDMA comparison

A follow-up on the same ConnectX-7 InfiniBand node setup described in Prefill and Decode Benchmark ran the three-role epd-arm3-epd allocation with one GPU per role. All 16 measured cells completed: 236/236 requests, with zero errors.

Transport verification

Update epd-deployment.yaml from the TCP walkthrough :

diff
 spec:
+  kvTransfer:
+    protocol: RDMA
   roles:
     - name: encode
       kind: Encode
       resources:
         accelerator: "1"
     - name: prefill
       kind: Prefill
       resources:
         accelerator: "1"
+        interface: "1"
     - name: decode
       kind: Decode
       resources:
         accelerator: "1"
+        interface: "1"

Prefill bound mlx5_5 with LID 21818; Decode bound mlx5_3 with LID 21813. Both Mooncake workers logged protocol rdma and registered their KV caches. The receive log recorded Received RDMA ready ACK; the captured logs contained no failed-transfer entries.

This verifies Mooncake KV transfer over InfiniBand RDMA between Prefill and Decode. NIXL ECCPUConnector still carried multimodal features between Encode and Prefill. The capture does not establish RDMA for that separate encoder-cache path. Each role used one GPU, so these cross-role transfers did not use NVLink.

Scope and trade-offs

RDMA reversed the 8k, concurrency-8 first-token disadvantage while retaining separate generation resources. It required InfiniBand interfaces on both KV-transfer roles; declaring RDMA alone does not establish a working transport. The TCP and RDMA measurements are separate runs on the same GPU model, not repeated transport-only trials.

Model, role counts and GPU budgets remained unchanged. Neither capture measures cross-node placement or RDMA encoder-cache transfer.

Single-request ITL p99 rose slightly in all four context shapes, despite lower median TTFT and higher throughput.

Limitations

  • One run per configuration, with 8–24 requests per stream or cell. Tail percentiles have limited sample support.
  • Unequal GPU allocations prevent an equal-cost throughput or per-GPU efficiency conclusion.
  • All serving roles shared one GPU node. Cross-node placement and bandwidth were not measured.
  • The initial capture used cross-Pod TCP over eth0; the follow-up verified InfiniBand KV transfer. Neither establishes cross-Pod NVLink.
  • The configurations ran sequentially with warmed model weights. Cache state and execution order were not independently controlled.
  • Encoder-cache, prefix-cache and compute-isolation effects were not measured separately.
  • Completion limits were fixed, but early stopping produced different output-token totals. Output throughput uses actual generated tokens.
