Elastic EP Benchmark

On one H100 SXM5 node, an expert parallelism (EP) collective expanded in place from four GPUs to eight. At concurrency 64 over TCP, time to first token (TTFT) p50 fell 2.50× (6,509.231 ms to 2,598.867 ms), while single-request generation slowed and output throughput fell in all six cells. The live expansion stream completed 439/439 requests with zero errors.

The initial suites describe cross-Pod TCP. The separate InfiniBand RDMA comparison records the matched follow-up.

Summary

One ModelDeployment (b2-elastic-ep in gpustack-bench) kept tensor parallelism (TP) = 2 per member while data parallelism (DP) width grew from 2 to 4 (EP world size 4 → 8 GPUs). Existing Pods kept their UIDs and zero restart counts. Elastic EP defines the profile and resize contract.

Doubling the GPU count over TCP did not raise throughput. Only one API server accepted requests in both states.

  • Choose online width growth when process continuity and concurrency-64 first-token relief justify extra GPUs (especially over InfiniBand RDMA, where width 4 also led concurrency-64 output).
  • Choose width 2 on TCP for lower concurrency, throughput and token-generation latency. Even at concurrency 64 on TCP, end-to-end p50 rose at width 4 (11,487.169 to 12,154.350 ms).

Benefits

  • Expanded 4 → 8 GPUs in place while keeping the serving master and original GPU worker; live load completed 439/439 requests with zero errors.
  • Cut concurrency-64 TTFT p50 2.50× (6,509.231 to 2,598.867 ms) and TTFT p95 (8,708.596 to 4,789.148 ms).

End-to-end p50 still rose from 11,487.169 to 12,154.350 ms at concurrency 64.

Trade-offs

  • Single-request ITL p50 rose 83.0% (8.566 to 15.675 ms), and concurrency-64 ITL p50 rose from 16.522 to 30.270 ms across the four-Pod TCP collective.
  • Output throughput fell in all six TCP cells (109.586 to 61.020 tok/s at concurrency 1; 1,145.131 versus 1,121.379 tok/s at concurrency 64).

The capture does not isolate collective, TCP and single-API-server overhead separately.

Results

Suite 1: Serving width comparison

Each state ran one sweep of target 1,024-input / 256-output-token requests (observed prompts 1,021–1,025 tokens). Concurrency 1, 4 and 8 used 32 requests; concurrency 16 used 64; concurrency 32 and 64 used 128, each excluding four warm-up requests. All 416 measured requests per state completed with zero errors. Output throughput divides actual generated tokens by cell wall time.

Over TCP with one API server, width 4 (8 GPUs) beat width 2 (4 GPUs) on TTFT only at concurrency 64 (2.50× lower TTFT p50: 6,509.231 to 2,598.867 ms; TTFT p95 8,708.596 to 4,789.148 ms), with ITL p99 nearly flat (157.753 versus 155.538 ms).

Across all six concurrencies, width 4 slowed ITL p50 (up 83.0% at concurrency 1: 8.566 to 15.675 ms) and lowered output throughput, and end-to-end p50 still rose at concurrency 64 (11,487.169 to 12,154.350 ms).

Time per output token (TPOT) measures per-request generation time per token; inter-token latency (ITL) measures streamed-token gaps. Bold values mark lower latency or higher throughput within each matched pair.

Live resize

A concurrency-8 stream (1,024/256 shape) ran across the width 2 → 4 patch and completed 439/439 requests in 264.227 seconds (264.23 s) with zero client errors. The capture recorded zero client-facing HTTP 503 responses and 10 /health HTTP 503 responses on the master during re-rendezvous.

Verification

Final observation reported generation 2, stable width 4 and reason native ranks and forwards agree. ReplicasUpToDate stayed Unknown/RolloutNotObserved. The master, CPU head and original GPU worker kept their UIDs and zero restart counts.

Master completion access logs rose from 880 before State 3 to 1,320 at finish (including warm-up and calibration). No Router was configured; client JSON establishes completion and errors. After deletion, Devices reported all eight H100 GPUs with remaining = 1600000.

InfiniBand RDMA comparison

A follow-up on the ConnectX-7 InfiniBand node from Prefill and Decode Benchmark expanded width 2 → 4 at TP = 2. Selected final cells completed 416/416 requests per width with zero errors.

NCCL logged Using network IB with GPU Direct RDMA enabled, moving the cross-Pod allgather_reducescatter collective onto InfiniBand while intra-Pod TP stayed on NVLink. Because --gpu-memory-utilization also changed (0.90 → 0.85), the runs do not isolate transport alone.

RDMA serving widths

In this separate InfiniBand follow-up (--gpu-memory-utilization 0.85), RDMA cut width-4 concurrency-64 TTFT p50 6.96× (2,598.867 to 373.486 ms), raised output 3.35× (1,121.379 to 3,755.290 tok/s) and cut ITL p50 (30.270 to 10.838 ms). Within RDMA at concurrency 64, width 4 beat width 2 by 8.23× on TTFT p50 and 1.64× on output, reversing TCP.

Exceptions remain: width 2 kept higher RDMA output at concurrencies 1–32 and lower single-request ITL p50 (6.111 versus 6.979 ms), and RDMA width 2, concurrency 4 regressed ITL p99 from 12.290 to 68.396 ms.

Resize verification

Live expansion load completed 813/813 requests in 261.794 seconds with zero errors. Surviving Pods kept their UIDs with zero restarts across all five final Pods, and generation-2 observation confirmed effective and stable width 4.

Observation Captured interval
New GPU Pods created About 5 seconds after the patch
Both new workers registered with Ray About 13 seconds after the patch
RoleKindsReady and EndpointEligibility became True About 167 seconds after the patch
Final observation Effective width 4; exact convergence time not recorded

Ray registration does not prove collective readiness. The harness timer polled a missing current_width field, so its 748-second value is not a convergence time; read effective.Value and stableWidth instead. The 2,134 total completion lines span width 2, expansion load and both width-4 passes.

RDMA width trade-offs

  • Choose RDMA width 4 for high-concurrency peaks (concurrency 64), where it led both TTFT and output throughput.
  • Choose RDMA width 2 for concurrencies 1–32 or lowest single-request ITL p50.

The follow-up supports high-concurrency InfiniBand expansion without proving linear scaling or transport-only causality.

Limitations

  • Single-node H100 captures with one sweep per width give no confidence intervals for small deltas.
  • State 1 used four GPUs and State 3 used eight (in-place capacity growth, not equal-GPU efficiency).
  • Only width 2 → 4 at TP = 2 ran; cross-node expansion, other collectives and scale-down were not tested.
  • Neither capture measures cross-Pod NVLink or isolates transport cost from collective size and memory-utilization changes.
  • Single-API-server internal load balancing (Internal LB) ran; per-rank HTTP serving was not measured here.
  • The 12-second phase check is not an effective-width timer; zero client errors do not guarantee uninterrupted readiness or stable token gaps during every resize.
  • Retained UIDs and restart counts prove Pod continuity, not unchanged engine internals; Ready does not imply every condition was true.
